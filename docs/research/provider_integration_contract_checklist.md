# Exhaustive Provider Integration Contract Checklist

This document lists the information to fetch to fully describe a provider's integration contract, regardless of whether the provider uses OAuth, API keys, webhooks, or a proprietary authentication mechanism.

## 1. Provider Identity and API Metadata

- [ ] Provider name and description
- [ ] Official website
- [ ] Developer portal URL
- [ ] Official API documentation URL
- [ ] API reference URL
- [ ] API version(s) and versioning policy
- [ ] Base URL(s) for each API version
- [ ] Separate URLs for authentication, token exchange, and other API services
- [ ] Production, sandbox, test, and staging environments
- [ ] Regional API hosts or data-residency endpoints
- [ ] API availability by country, region, account type, or subscription
- [ ] API lifecycle status: active, beta, deprecated, sunset
- [ ] Changelog and release notes
- [ ] Official SDKs, code examples, Postman collections, OpenAPI/Swagger specifications
- [ ] API terms of service, acceptable-use policy, and developer agreement
- [ ] Support channels and status page

## 2. Authentication Methods

Fetch **every authentication method supported by the provider**, not just the default one.

- [ ] OAuth 2.0 authorization code
- [ ] OAuth 2.0 authorization code with PKCE
- [ ] OAuth 2.0 client credentials
- [ ] OAuth 2.0 device authorization grant
- [ ] OAuth 2.0 refresh-token flow
- [ ] OAuth 1.0a
- [ ] API key
- [ ] Personal access token
- [ ] Basic authentication
- [ ] Bearer token
- [ ] JWT-based authentication
- [ ] Signed requests, HMAC, or request-signing schemes
- [ ] Service accounts
- [ ] Client certificates / mutual TLS
- [ ] Username and password, if explicitly supported
- [ ] Custom or proprietary authentication
- [ ] Public endpoints that require no authentication
- [ ] Multiple authentication methods supported for the same API

For each method, fetch:

- [ ] Authentication type and intended use case
- [ ] Required credentials and their exact names
- [ ] Credential format and validation rules
- [ ] Where credentials are obtained
- [ ] Whether credentials are generated by the provider or developer
- [ ] Whether the integration uses provider-managed OAuth or its own OAuth application
- [ ] Whether authentication is for a user, organization, workspace, application, or service account
- [ ] Whether the method is suitable for server-side, browser, mobile, or machine-to-machine applications
- [ ] Whether client secrets are required
- [ ] Whether a client secret can be safely omitted for public clients
- [ ] Required headers, query parameters, cookies, or request-signing fields
- [ ] How credentials are transmitted
- [ ] Credential expiration, rotation, revocation, and regeneration
- [ ] Token lifetime, refresh behavior, and reauthorization requirements
- [ ] Whether multiple credentials can coexist
- [ ] Authentication-specific restrictions and known limitations
- [ ] Official examples of successful and unsuccessful authentication

## 3. OAuth-Specific Contract

- [ ] Whether separate applications or credentials are needed per environment
- [ ] Whether test and production applications differ
- [ ] Redirect URI / callback URL requirements
- [ ] Exact redirect URI matching rules
- [ ] Allowed URI schemes, ports, paths, wildcards, and localhost behavior
- [ ] Whether multiple redirect URIs are allowed
- [ ] Whether the redirect URI can be changed later
- [ ] Whether the provider requires a domain or website to be verified

### Authorization Flow

- [ ] Token endpoint URL
- [ ] Revocation endpoint URL
- [ ] Token introspection endpoint URL, if supported
- [ ] Discovery or metadata endpoint URL, if supported

- [ ] Required `scope` format and delimiter
- [ ] Required `state` behavior
- [ ] PKCE support and requirements
- [ ] Supported PKCE methods
- [ ] `nonce` requirements, where applicable
- [ ] Audience, resource, tenant, organization, or account parameters
- [ ] Provider-specific authorization parameters
- [ ] Consent screen behavior
- [ ] Login and account-selection behavior
- [ ] User consent and administrator consent requirements
- [ ] Exact authorization URL construction rules
- [ ] Expected success callback parameters
- [ ] Expected error callback parameters
- [ ] Authorization-code lifetime and single-use behavior
- [ ] Token-exchange request format
- [ ] Token-exchange authentication method
- [ ] Token response schema
- [ ] Access-token type and expected format

- [ ] Error codes and recovery procedures

### OAuth Scopes and Permissions

- [ ] Complete list of supported scopes
- [ ] Exact scope identifiers and case sensitivity
- [ ] Description of each scope
- [ ] Read/write/admin distinctions
- [ ] User-level versus organization-level permissions
- [ ] Which API operations require each scope
- [ ] Which scopes are mandatory versus optional
- [ ] Scope dependencies and combinations
- [ ] Default scopes granted when none are specified
- [ ] Restricted, sensitive, or privileged scopes
- [ ] Whether scopes require administrator approval
- [ ] Whether scopes require provider verification or review
- [ ] Whether scope access varies by plan or account
- [ ] Whether scopes are additive or replaced during reauthorization
- [ ] Minimum scope set for each desired capability
- [ ] Scope-related errors and troubleshooting instructions

## 16. Documentation Evidence and Completeness

For every fetched fact, capture the following metadata:

- [ ] Exact claim or extracted value
- [ ] Source URL and page title
- [ ] Source type: official documentation, developer portal, OpenAPI, SDK, example, community post, or observed behavior
- [ ] Relevant section, heading, or code location
- [ ] Date accessed and source publication/update date, if available
- [ ] API version or product version the evidence applies to
- [ ] Whether the fact is explicitly documented or inferred
- [ ] Confidence level
- [ ] Conflicting sources, if any
- [ ] Whether the claim was independently verified
- [ ] Known limitations or missing evidence
- [ ] Whether the source requires login or account access
- [ ] Whether the source is accessible and still valid
- [ ] Whether the information is stable or likely to change

**Important:** distinguish between `supported`, `unsupported`, and `unknown`. If documentation does not mention refresh tokens, webhooks, or a particular endpoint, that alone does not prove the provider lacks that feature.

## 18. Three Distinct Parts of the Contract

Keep these three categories separate:

1. **What the provider supports** — capabilities, API behavior, authentication methods, and restrictions.
2. **What a developer must configure** — credentials, application registration, redirect URLs, permissions, approvals, and infrastructure.
3. **What the integration runtime must implement** — authorization, token management, API calls, pagination, retries, webhooks, error handling, and lifecycle management.

Keeping these separate prevents API documentation from being mistaken for a complete integration contract.
